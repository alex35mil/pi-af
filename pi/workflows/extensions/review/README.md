# Review extension

Registers native deferred `review_epic`, `review_task`, `review_gig`, and `record_review_response`. See [tool discovery](../../references/tools.md). Strict schemas admit Epic planning reviews and Task/Gig plan, interim, final, `conflict-plan`, and `conflict-merge` reviews; each Task/Gig category is its own strict object, so `subject` exists only for interim and the required `resolution` only for `conflict-plan`. A `conflict-plan` round records `conflict.json`: the branch, target, fetched target SHA, resolution, and pre-merge base, which is the branch head or, for an unpushed merge of that target, its first parent. A `conflict-merge` round requires the newest `conflict-plan` round to have approved and the branch head to be a merge whose parents equal that round's pre-merge base and target SHA, and records `merge.json`. Plan rounds copy `plan.md` (or `epic.md`), and final rounds copy the kind's `result.md` or `report.md`, into `candidate.md`. A final round's prompt carries the branch diff from the merge base with the target, preferring `origin/<target>`, to the working tree, plus `git status`, so locally committed steps are reviewed too. A final round without `plan.md` (the direct path) names the brief as the requirement.

**Passes.** `../__lib/review-rounds.ts` owns the round model shared with integrations: round discovery, `outcome.json`, `pass.json`, and the category's cycle (`none`, `awaitingVerification`, `finished`). `pass.ts` chooses the next pass: a review, or after a blocked review, one verification pass whose prompt carries that round's findings, the recorded responses, and, for documents, a diff of `candidate.md` against the verified round's. A finished `plan` or `final` cycle refuses another review without a `newReview` reason; `interim`, `conflict-plan`, and `conflict-merge` restart freely. A failed round isn't a pass. `integrations/creation.ts` refuses a new PR, and `__lib/epic-acceptance.ts` refuses Task list acceptance, until the relevant cycle finished. Rounds without `pass.json` aren't supported; entities in flight are finished before upgrading.

Also registers `review_pull_request` and `record_pull_request_review_response` for [incoming PRs](../../references/pr/incoming.md). The review tool accepts `reference`, exact configured PR-get `evidence`, a complete local `dossierPath`, and explicit `sourcePaths` for every referenced source/diff/dependency file; the response tool uses the original evidence, returned round number, all findings and status. These distinct adapters require no entity or lifecycle. Review artifacts live under `.project/.local/pull-requests/<number>/reviews/<base-sha>-<head-sha>/review-NNN/`, with write-once source snapshots in `inputs/`. Checkout, state/diffs and working evidence remain at the PR root. Existing review records are not moved or rewritten automatically; round discovery and adjudication use only this review namespace. Each pass freezes its own source bytes so successive uncommitted fix drafts at the same head cannot change earlier evidence. Each reviewer pass records the complete dossier and original-to-saved source-file map, then runs from the trusted maintainer checkout using those immutable inputs. They never call providers, publish, execute contributor code or authorize mutations.

The review subsystem owns prompt assembly, pass choice, and signoff validation. `findings.ts` owns finding fields, the two severities (`blocking`, `note`), report parsing, and canonical rendering, including each report-sourced severity beside its ID/title. A report is `blocked` exactly when it has a blocking finding; parsing rejects a mismatch. Parsing accepts exactly one report object surrounded by prose or a code fence, then validates it strictly and names missing or unexpected keys. `agent.ts` owns read-only subprocess execution with shared rules and permissions, in a private session directory that `round.ts` creates per round and always deletes. `model.ts` resolves an explicit reviewer override through Pi’s public model resolver; otherwise it uses the configured startup default, not the parent session’s current model. When Claude Code is selected, it obtains the already-loaded enabled provider extension’s entry point from native `claude-code-status` command provenance and explicitly loads only that provider alongside rules and permissions. It installs nothing and does not guess package paths or execute unrelated extension factories. Standard providers retain native child selection. The child keeps `--no-extensions`, `--no-skills`, and `--no-prompt-templates`. Its tool set is a `ReviewerToolset`: entity reviews get `read,grep,find,ls,git_read` and load `git-read.ts`; incoming-PR reviews get only `read,grep,find,ls`. No write, Bash, Codemode, workflow, or MCP executor is granted. Reviewer tools run under the user's permission settings with no UI, so under `defaultMode: "ask"` they must be allowed by name or they're blocked. `round.ts` shares execution/report/transcript/outcome persistence across entity and PR adapters. Entity rounds record only rejected and needs-decision findings in `response.json`; incoming-PR rounds keep the complete-list `response.md`. When a successful run returns an invalid report, it resumes that session once with the validation error and the previous output in full; both runs share `agent.jsonl`, `transcript.md`, and `stderr.txt`. If that also fails, it writes `invalid-report.md` and includes the output, marked unvalidated, in the thrown error. Entity reviews (`index.ts`) add a fixed pause after two consecutive failed rounds per category; incoming PR reviews have no pause. `pull-request.ts` owns the PR evidence adapter, source-file snapshots, and untrusted-data prompt. Existing entity gates remain in `index.ts`.

`git-read.ts` registers `git_read` only in reviewer subprocesses. It runs one allowlisted subcommand through `execFile` without a shell, with `GIT_TEST_DISALLOW_ABBREVIATED_OPTIONS=1`, hooks, fsmonitor, pager, colour, external diff, signature verification, content filters, and custom merge drivers disabled, and refuses inherited relocation variables. It refuses arguments that write files, run programs, or read untracked, ignored, or out-of-repository content, including any abbreviation of a refused long option, and requires `--write-tree` for `merge-tree`. It reads Git objects and tracked files, so path-based `read` deny rules don't apply to committed content. Every entity review prompt names it through the shared `REVIEW_GIT_INSTRUCTIONS`.

Operational contracts: [planning](../../references/planning.md), [adjudication](../../references/review.md), and [artifact layout](../../references/artifacts.md). Entity/kind review criteria remain explicit in the prompts.
