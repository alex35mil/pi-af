# Incoming PR checkout tooling

Selection, safety assessment, contributor access and approvals are in [incoming PR handling](./incoming.md); the merge, Done, and cleanup process and cancellation are in [shipping](./shipping.md). The named incoming-PR checkout tools, registered by the PR extension, own initialization/fetch, checkout/review setup, validated transitions, target observation, standard rebase and its immediate SHA-pinned lease-protected PR update. The agent must not reconstruct Git orchestration in Bash. No manual fallback is permitted after refusal, failure or unavailability; preserve work and resolve the blocker. Reload trusted extensions when the registered tool is unavailable.

## Inputs and approval scope

Every operation takes `reference` and actual configured `pull_request_read:get` `evidence` (tool, arguments and unchanged response). The tool derives repository URLs, full branch refs and private paths from this identity. Obtain fresh provider evidence before mutations and on resume; validation checks consistency, not independent provenance/freshness. There are no arbitrary URL/path/ref/command overrides or approval booleans.

GitHub Git transport is SSH (`git@github.com:<owner>/<repo>.git`) for fetch, exact remote-tip observation and push, using existing trusted SSH authentication. Do not configure HTTPS credentials or change parent/global Git configuration. HTTPS PR URLs and registered provider evidence remain identity/API inputs, not transport overrides.

The normal update flow is **standard rebase → approved conflict resolution → immediate `--force-with-lease` PR update → approved fixes and maintainer testing**. Before `rebase_incoming_pr`, establish contributor consent/authenticated access and approval of the exact source head, target SHA, destination and lease. This one approved operation set includes rebase's replacement commits and its immediate push; `continue_incoming_pr_rebase` also pushes immediately when the last approved conflict is resolved. It does not authorize later fix commits/pushes, tests, GitHub review publication or merge.

Keep all these checkout operations outside skill-derived allows. Existing native-tool permissions and conversational gates both apply; change no permission settings automatically. Local state and observations are facts, not approval tokens.

Repeated valid prepare/review/fixes calls do not reset drafts or re-fetch over work. Mutation mismatches, incompatible/unmanaged paths, unexpected changes and incomplete operations stop without cleanup, reset, stash, abort, skip, force checkout, automatic adoption or branch deletion. Inspect and agree on recovery rather than bypassing the tool.

In contributor review only, detached HEAD is the original common ancestor while index/source remain the original PR head. **Do not edit, stage/unstage, commit or push in this phase.** Restore clean contributor HEAD through `begin_incoming_pr_fixes` before rebase or static edits.

## Rebase and publication semantics

Use standard rebase, not merge-into-PR or preserve-merges. PR commits are replayed onto the approved target as a straight line; merge commits are not recreated. Ordinary Git handling of already-upstream/empty commits applies; returned messages retain Git's skipped-commit information. No interactive todo editing, exec commands, autosquash, autostash or updates of unrelated refs.

Provider-reported base/head evidence stays unchanged. `observe_incoming_pr_target` reads the actual `refs/heads/<base-ref>` tip and contributor branch separately. A changed tip before starting requires reassessment and renewed exact approval. During conflict resolution the active target and lease remain pinned; later observations never replace them silently.

Conflicts are expected inspectable states. No push while conflicts remain. Git's rebase sides are **ours = target plus commits already replayed**, **theirs = contributor commit being replayed**. Return unmerged index stages, affected paths, native progress and diffs. The agent proposes/edits approved resolution contents; the tool performs resolution staging and continuation. Mechanical validation is not proof that a resolution is semantically correct or tested.

On successful rebase, verify native completion, target ancestry and a clean detached result, then immediately push the recorded result SHA to the existing contributor repository/ref. The push uses the explicit option `--force-with-lease=refs/heads/<head-ref>:<observed-pre-rebase-head-sha>` and an explicit result-SHA-to-that-ref refspec. Never use plain `--force`, an implicit tracking-ref lease or the base repository as a fork destination. A contributor update rejects the lease and preserves remote work plus the local rebased result.

Publication is recorded as pending, attempted/uncertain, rejected with observed head, or confirmed. Save the attempted result/lease before sending. A lost response can follow a successful remote update: read the exact remote head before retrying. Already published results are confirmed without repeating the push; changed/deleted branches are not overwritten/recreated. Cancellation and incomplete operations retain their actual state, never grant a fresh lease or trigger automatic rollback. Report confirmed remote completion even when a later local check fails.

After an HTTPS authentication failure with a saved completed rebase, use approved `publish_incoming_pr_rebase` recovery over SSH with the same recorded result and original lease. No checkout recreation, refetch, rebase rerun, lease refresh or state migration is needed. An SSH authentication failure preserves that result and lease; resolve access separately, with no HTTPS or manual Git fallback.

After confirmed publication obtain fresh actual PR evidence for the new head; do not edit an old response to manufacture it. Later fixes use the confirmed published head as their baseline. Before any separately approved fix commit, verify actual HEAD equals the freshly verified published contributor head. Keep later fixes **uncommitted throughout maintainer review, discussion and revision**; ordinary fix commits/pushes, review publication, testing and GitHub merge retain separate approvals.

## Additive fixes and cleanup

Use `commit_incoming_pr_fixes` and separately approved `publish_incoming_pr_fixes`, never a shell commit/push that bypasses managed state. An approved fix commit must have the recorded parent/tree/message and clean exact result; unexpected staged/changed/untracked paths are preserved. `committingFixes` can recognize an already-applied exact commit after interruption; `committedFixes` remains unpublished until remote confirmation. A rejected/uncertain normal push preserves the commit and never forces, rebases or silently refreshes its source.

The saved rebase result is historical integration evidence, not permanently the current published baseline. Confirmed additive publication advances `baselineSha` while preserving original evidence, historical rebase facts and valid inspection/resume. Original-to-rebase comparison stops at that recorded integration, separate from published and pending fixes.

Cleanup is part of the exact shipping and merge operation set after confirmed merge and applicable native Project Done. Supply `completion` with scoped field/item evidence for a configured Project, or explicit `forgeOnly` only when no GitHub Project is configured. Clean known object-only/contributor-review representation is removable; maintainer drafts, pending commits/rebases, extra local refs/worktrees or unsafe paths are not. Confirm unsaved-buffer safety before destruction. No checkout means no-op, not initialization.

`removing`, `deleting` and `removed` represent owned local removal facts, not PR lifecycle. Inspection remains available without recreating source. Retired-source removal resumes only at its recorded private path and preserves new work at the original checkout path. Keep notes, state/evidence/diffs and immutable reviews. A later failure never reverses confirmed merge/Done; cancellation closes the PR and keeps local work, with no cleanup.

## Returned state and private evidence

Active-checkout output includes relative/absolute paths, unchanged original `revision`, actual input `providerRevision`, original `reviewBaseSha`, current published `baselineSha`, separate remote `observation`, active/completed `rebase_incoming_pr` facts, publication status, Git messages, phase and `phaseValid`, actual HEAD/commit/index/worktree comparisons (`indexMatchesBaseline` refers to the published baseline), `fixCommit` intent/result when present, staged/unstaged state, native operation and unmerged stages, untracked paths including ignored additions and parent-verification outcome.

Keep these files at `.project/.local/pull-requests/<number>/`, not inside its review rounds:

- `checkout/`: independent source repository with its own real `.git`, HEAD and index.
- `checkout.json`: original evidence/identity, observed tips, validated progress, working baseline and completed publication facts; never approval or workflow lifecycle.
- `checkout-inspection.json`: complete latest observations and phase validation.
- `checkout-contribution.diff`: original merge-base-to-original-PR contribution.
- `checkout-rebase.diff`: original source head to current rebased/intermediate result; upstream integration is not labeled as a later fix.
- `checkout-conflicts.diff`: current combined conflict comparison, with unmerged stage details in the inspection record.
- `checkout-fixes.diff`: current confirmed baseline-to-local tracked draft or pending additive fixes; empty during object preparation or rebase.
- `checkout-published-fixes.diff`: additive fixes already published after the latest integration point, separate from the current draft.
- `checkout-untracked.json`: complete new-file listing, including ignored additions. Read relevant contents explicitly; do not stage later fixes merely for visibility.

Output is limited to 2000 lines/50KB and points to full private evidence on truncation. These current inspection files are mutable working evidence. Freeze relevant original/rebase/resolution/fix/source evidence through `reviews/<provider-base-sha>-<provider-head-sha>/review-NNN/inputs/` before independent review. Earlier review records and source snapshots are never moved or rewritten.

## Safety boundary

The tool uses direct argument arrays, exact independent `.git`/worktree paths and private-path validation, including dangling symlinks. No parent-repository discovery or contributor resource loading. Inherited Git relocation/configuration overrides are refused before context/artifact readers; unset those host overrides explicitly and retry only the approved operation. Same-checkout operations share the existing file-mutation queue.

Git controls disable hooks (`core.hooksPath=/dev/null` on the supported Unix host), fsmonitor, configured clean/smudge/process filters, external diff/textconv helpers, custom merge-driver commands, signing/editor helpers, rerere reuse, maintenance and submodule recursion, including push-time recursion. A blocked custom merge driver reports conflict instead of executing it or silently declaring a successful replacement merge. Use an empty init template; do not automatically fetch LFS/submodule assets. No parent/global configuration changes.

Compare parent branch/HEAD, raw index/configuration, status and working-file evidence before/after success, conflict and failure without parent index refresh or automatic restoration. Keep the agent/shell/editor/reviewer rooted in the trusted parent; use full checkout-prefixed file paths and actual lines. Do not activate contributor instructions, extensions, rules, packages or editor/environment configuration; disable editor project tooling separately. Inspect symlinks as links/Git objects, not by following outside the checkout.

A nested checkout is not a sandbox. Rebase and its immediate publication do not authorize contributor tests/builds/installs/scripts/hooks/plugins/formatters. Obtain separate exact-command and appropriately isolated environment approval; report unavailable runtime checks as **not run**. Existing Delta does not automatically choose this nested Git repository from parent cwd, and Pi autocomplete skips ignored checkout files. Direct file/line references work; this change modifies neither plugin.
