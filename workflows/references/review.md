# Review finding adjudication

Use this flow for every Epic/Task/Gig plan, interim, and final review. Phase rules ([Phase](./phase.md)): plan review, corrections, presentation, and waiting for plan approval remain in Planning. Interim/final review and local user review of delivered work use Self-Review; permitted implementation corrections and verification use Execution before returning to Self-Review. Lifecycle remains In Progress throughout these local loops. Reconcile native Phase before starting or presenting review. The review tool's plan/interim/final category remains separate from workflow Phase. A blocked-review confirmation pause stays in Planning for plan reviews or Self-Review for interim/final reviews until the user permits corrections.

1. The reviewer returns one validated structured report. The review tool passes its findings through the shared canonical renderer before writing `review.md` or returning them to the main agent. Raw reviewer prose is never a human-facing finding list.
2. Validate every finding against repository evidence, active rules, and the credible-complexity requirements. Review current source documents against the [reviewed document shape](./artifacts.md#reviewed-document-shape): Overview accurately represents the complete detailed contract or evidence, keeps material limitations visible, and stays synchronized with the source. Plan highlights reflect accepted scope and behavior; report/result overviews communicate the conclusion or delivered outcome without replacing supporting evidence.
3. Assign one resolution:
    - `accepted`: evidence confirms the concern and established requirements determine the correction without a new user-owned decision.
    - `rejected`: evidence disproves the concern, it conflicts with an approved decision or higher-priority rule, or it lacks required causal support. Record the exact reason and evidence.
    - `needs user decision`: evidence supports the concern, but resolving it requires an unsettled product, domain, UX, scope, priority, or tradeoff decision. Present that decision before editing and wait for the user's direction.
4. Call `record_review_response` with every adjudicated finding. Keep its stable label and use direct plain language in the canonical fields: `Problem`, `Use case`, `Impact`, `Resolution`, and `User decision needed`. The tool writes `response.md` and returns those exact same rendered bytes. Present that returned Markdown unchanged in chat before the next workflow action. Never manually recreate, paraphrase, summarize, or reformat the list.
5. Before applying findings, check optional `.project/config.json` `reviews.userConfirmationAfter`. When absent, the confirmation checkpoint is disabled. When a valid `blocked` signoff reaches the configured consecutive-block threshold for that entity and phase, stop immediately before corrections or correction verification. Present every round in that batch using its labeled canonical adjudicated response and state whether it contained at least one valid blocking issue at review time. A block is legitimate when at least one valid blocking issue required correction or a user decision; incorrect secondary findings do not invalidate an otherwise legitimate block. Ask only `Was blocked review NNN legitimate?` for one round or `Were blocked reviews NNN, ... legitimate?` for multiple rounds, then wait.
6. If the user judges every round legitimate, apply accepted findings from the current threshold round at the owning abstraction, update `.local/notes.md`, the mutable candidate or implementation, and the applicable `result.md` or `report.md`, then start a fresh batch. If any round was illegitimate, diagnose the reviewer guidance or tooling before proposing a correction. Resolve mixed or unclear judgments before correcting the current round or running another review. Store no approval token or durable continuation state.
7. Outside a pending confirmation checkpoint, apply accepted findings and user decisions at the owning abstraction, then run affected verification. Keep the applicable completion artifact synchronized with actual results and report any planned checks not run with their reasons.
8. When no finding needs a user decision, accepted/rejected agent-owned findings may proceed through correction and another review after their required chat presentation and verification. Count valid `blocked` signoffs separately by entity and phase. A valid `approved` signoff resets the current partial batch; failed or malformed output neither counts nor resets it. Continue until signoff is approved and no user note remains unresolved.

Keep the complete round under `.local/reviews/<phase>-NNN/`. `report.json` is the validated machine report; `review.md`, `response.md`, and chat use the one shared finding renderer; and `outcome.json` stores execution/signoff state used to calculate each configured blocked-review batch. Accepted corrections and decisions must be reflected directly in their current authoritative artifacts; never require the user to interpret local reviewer artifacts.

## Incoming PR adjudication

[Incoming PR review](./pr/incoming.md) reuses the validated report, canonical renderer, and evidence standards above, without initialized-entity phase, plan/result or correction-loop requirements. Validate each finding against the exact revision, requirements, source and credible causal evidence. Classify it as accepted, rejected with evidence, or needing a maintainer decision. Record every finding through `record_pull_request_review_response` using its stable label, the returned round number, and that round's original exact PR-get evidence. Present the tool's returned Markdown unchanged; finding headings carry ID and severity from the saved report. Identify PR/revision, coverage and verification limitations separately. Ask about unsettled domain decisions before proposing a resolution. A local signoff is critique only: publication, fixes, pushes and merges retain their separate explicit approvals and the incoming workflow's execution boundary. Never run or apply contributor changes merely to resolve a review finding.
