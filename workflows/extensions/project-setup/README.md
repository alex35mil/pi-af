# Project setup extension

Registers `/project-setup` and the setup-owned `inspect_project_setup`, `prepare_artifacts`, `configure_mcp`, `inspect_permissions`, `configure_permissions`, `inspect_linear_workspace`, `preview_linear_status_setup`, `apply_linear_status_setup`, the named GitHub inspection/preview/apply operations, the label setup operations, and side-effect-free `render_incoming_pr_intake` tools.

`incoming-pr-intake.ts` renders an opt-in fork-only metadata workflow with a verified full-commit Action pin, exact selected Project/repository, Actions secret name and activation prerequisites. It only adds membership, relying on the native Backlog default; no Status writes, contributor checkout/execution, credentials, provider changes or deployment. Setup inspection includes the managed `.github/workflows/incoming-pr-project.yml` path, and the exact local file requires approval. See [automation](../../references/pr/automation.md).

The command and read-only inspection tool share `inspectProjectSetup`. Natural-language setup obtains the same credential-safe GitHub identities from fetch remotes, setup/Git/binding context, and credential-redacted MCP inventory without requiring valid workflow configuration, writing files, or calling providers. The tool returns JSON text and structured details; only the command injects a kickoff message. Provider availability and mutation approval remain separate from configured-registration inspection.

GitHub setup lives in `github-project.ts`: repository identity/ownership and title-default discovery (`inspect_github_repository_setup`), owner-scoped Project discovery (`inspect_github_project_setup`), selected-Project/view inspection (`inspect_github_project`), and exact `preview_github_project_setup` / `apply_github_project_setup` hash-approved provisioning of repository-reference short descriptions, fields, association, and view presentation. Its `GitHubClient` also carries the repository label calls that label setup uses. Short descriptions use `Repository: https://github.com/<owner>/<repo>` from the resolved setup repository, with current/replacement text in existing/resumed previews and exact read-back; Project README content is preserved. Personal repositories use Project-contained Priority without a scope question. Board defaults use semantic field references and an exact distinct visible-field selection, with no card-field ordering promise. Board permutations are normalized at the read boundary for matching, approval hashes, recovery, and default-view fingerprints; table field order remains significant. Fresh empty Projects get a REST-created Board with Status columns, no swimlanes, and the configured Priority sort; full read-back precedes deletion of only the captured unchanged generated default view. Existing/resumed Projects retain selected-view updates and preserve all views and unrelated settings. Count, slicing, and default repository remain guided UI steps requiring user confirmation; adopted views also retain manual column/group/sort configuration. Every mode/layout additionally returns a `defaultStatus` manual follow-up note: the available MCP tools and documented public APIs do not expose the native field-default setter, so the user must save the configured Backlog option as the configured Status field's default and confirm saved state before full setup completion. This remains required with default-repository opt-out. Built-in automations and existing item values are unchanged. Repository association and default repository remain separate setup choices. Presentation never enters runtime tracker configuration. See the [presentation contract](../../references/setup/github-project.md#presentation).

Personal Board creation addresses the owner by encoded login; field identifiers remain numeric. Shared request diagnostics report method/path and the failed setup stage, including REST response interpretation errors and specific view-verification mismatches. Failed create recovery reports candidate identities/checks alongside the original create failure; zero or multiple matching new Boards never trigger another create. Diagnostics redact the configured token, retain failed-write context when recovery reads also fail, and never print authorization headers or request bodies. A later invocation inspects the partial Project, explicitly selects its existing view as `resume-created`, and requires fresh preview/hash approval; no prior default-view deletion permission is inferred.

Label catalog setup lives in `label-catalog.ts` and `label-setup.ts`. `label-catalog.ts` is the pure planner: it compares the desired managed labels with the tracker's catalog and the previously applied set, and returns ordered actions and the decisions the user must answer. `label-setup.ts` registers `inspect_label_setup`, `preview_label_setup`, and `apply_label_setup`, with a GitHub adapter (REST labels, GraphQL usage counts) and a Linear adapter (GraphQL issue and Project labels). Apply refuses a changed `planHash`, confirms a failed write by reading the catalog again, verifies the catalog afterwards, and returns the configuration to save. The unknown-label rule, `isUnknownLabel`, lives in `../integrations/labels.ts` so runtime and setup share it.

MCP and permission configuration live in `mcp.ts` and `permissions.ts`, with shared local-settings exclusion in `local-settings.ts`. Read-only `inspect_permissions` checks candidate MCP rules against persistent global/project/local settings and the live MCP catalog. It reuses the permission extension's parser, coverage analysis, and matcher; catalog refresh replaces metadata and shutdown disposes the listener. `configure_permissions` takes explicit `target`, `allow`, and `ask` fields, rechecks policy, and merges approved additions without weakening ask/deny or replacing unrelated settings. Covered, blocked, and unavailable allows are reported and skipped; partial read-only blockers remain visible. Permission writes use Pi's per-file mutation queue. No-op calls change neither settings nor exclusions. Setup recommends active-provider reads and frequent tracker writes with full-tool/credential-scope warnings, leaving user selection, exact approval, and local/project persistence explicit. Linear status setup lives in `linear-statuses.ts`: a pure planner maps each lifecycle key to an existing status or a create, positions creates after the previous key's status, and blocks on ambiguous or colliding names; apply rechecks the `planHash`, creates workspace Project statuses before team issue statuses, explains authorization rejections, confirms other failed creates by reading again, and verifies every mapping. It never renames, reorders, archives, or deletes statuses. The status defaults, create mutations, and `LinearApiError` live with the client in `../integrations/tracker/linear.ts`. `configure_mcp` gives every GitHub registration all workflow toolsets (`GITHUB_MCP_TOOLSETS`). Linear workspace inspection remains with its provider under `../integrations/tracker/linear.ts`, while shared project configuration remains under `../__lib/`. See [guided setup](../../skills/project-setup/SKILL.md) and the [setup contract](../../references/setup.md).
