# Project setup extension

Registers `/project-setup` and the setup-owned `inspect_project_setup`, `prepare_artifacts`, `configure_mcp`, `inspect_permissions`, `configure_permissions`, `inspect_linear_workspace`, and `provision_github_project` tools.

The command and read-only inspection tool share `inspectProjectSetup`. Natural-language setup obtains the same credential-safe GitHub identities from fetch remotes, setup/Git/binding context, and credential-redacted MCP inventory without requiring valid workflow configuration, writing files, or calling providers. The tool returns JSON text and structured details; only the command injects a kickoff message. Provider availability and mutation approval remain separate from configured-registration inspection.

GitHub setup lives in `github-project.ts`: repository identity/ownership and title-default discovery (`inspectRepository`), owner-scoped Project discovery (`inspect`), selected-Project/view inspection (`inspectProject`), and exact preview/hash-approved provisioning of fields, Kind labels, association, and view presentation. Personal repositories use Project-contained Priority/Internal ID without a scope question. Board defaults use semantic field references. Fresh empty Projects get a REST-created Board with Status columns, no swimlanes, and the configured Priority sort; full read-back precedes deletion of only the captured unchanged generated default view. Existing/resumed Projects retain selected-view updates and preserve all views and unrelated settings. Count, slicing, and default repository remain guided UI steps requiring user confirmation; adopted views also retain manual column/group/sort configuration. Repository association and default repository remain separate setup choices. Presentation never enters runtime tracker configuration. See the [presentation contract](../../references/setup.md#github-project-presentation).

Personal Board creation addresses the owner by encoded login; field identifiers remain numeric. Shared request diagnostics report method/path and the failed setup stage, redact the configured token, and retain failed-write context when recovery reads also fail. They never print authorization headers or request bodies.

MCP and permission configuration live in `mcp.ts` and `permissions.ts`, with shared local-settings exclusion in `local-settings.ts`. Read-only `inspect_permissions` checks candidate MCP rules against persistent global/project/local settings and the live MCP catalog. It reuses the permission extension's parser, coverage analysis, and matcher; catalog refresh replaces metadata and shutdown disposes the listener. `configure_permissions` takes explicit `target`, `allow`, and `ask` fields, rechecks policy, and merges approved additions without weakening ask/deny or replacing unrelated settings. Covered, blocked, and unavailable allows are reported and skipped; partial read-only blockers remain visible. Permission writes use Pi's per-file mutation queue. No-op calls change neither settings nor exclusions. Setup recommends active-provider reads and frequent tracker writes with full-tool/credential-scope warnings, leaving user selection, exact approval, and local/project persistence explicit. Linear workspace inspection remains with its provider under `../integrations/tracker/linear.ts`, while shared project configuration remains under `../__lib/`. See [guided setup](../../skills/project-setup/SKILL.md) and the [setup contract](../../references/setup.md).
