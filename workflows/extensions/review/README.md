# Review extension

Registers native deferred `review_epic`, `review_task`, `review_gig`, `record_review_response`, and the entity-specific `prepare_epic_plan_presentation`, `prepare_task_plan_presentation`, and `prepare_gig_plan_presentation` tools. See [tool discovery](../../references/tools.md). Strict schemas admit Epic planning reviews and Task/Gig plan, interim, and final reviews. The preparation tool validates and selects a reviewed snapshot and returns its source and target paths; the write tool presents the approval diff.

Also registers `review_pull_request` and `record_pull_request_review_response` for [incoming PRs](../../references/pr/incoming.md). The review tool accepts `reference`, exact configured PR-get `evidence`, a complete local `dossierPath`, and explicit `sourcePaths` for every referenced source/diff/dependency file; the response tool uses the original evidence, returned round number, all findings and status. These distinct adapters require no entity or lifecycle. Review artifacts live under `.project/.local/pull-requests/<number>/reviews/<base-sha>-<head-sha>/review-NNN/`, with write-once source snapshots in `inputs/`. Checkout, state/diffs and working evidence remain at the PR root. Existing review records are not moved or rewritten automatically; round discovery and adjudication use only this review namespace. Each pass freezes its own source bytes so successive uncommitted fix drafts at the same head cannot change earlier evidence. Each reviewer pass records the complete dossier and original-to-saved source-file map, then runs from the trusted maintainer checkout using those immutable inputs. They never call providers, publish, execute contributor code or authorize mutations.

The review subsystem owns prompt assembly, round discovery, signoff validation, optional configured blocked-review confirmation for initialized entities, and reviewed-snapshot selection. `findings.ts` owns finding fields, report parsing, and canonical rendering, including each report-sourced severity beside its ID/title; `agent.ts` owns fresh read-only subprocess execution with shared rules and permissions. `model.ts` resolves an explicit reviewer override through Pi’s public model resolver; otherwise it uses the configured startup default, not the parent session’s current model. When Claude Code is selected, it obtains the already-loaded enabled provider extension’s entry point from native `claude-code-status` command provenance and explicitly loads only that provider alongside rules and permissions. It installs nothing and does not guess package paths or execute unrelated extension factories. Standard providers retain native child selection. The child keeps `--no-extensions`, `--no-skills`, `--no-prompt-templates`, and only `read,grep,find,ls`; no write, Bash, Codemode, workflow, or MCP executor is granted. `round.ts` shares execution/report/transcript/outcome persistence and complete-list adjudication across entity and PR adapters. `pull-request.ts` owns the PR evidence adapter, source-file snapshots, and untrusted-data prompt. Existing entity gates remain in `index.ts`.

Operational contracts: [planning](../../references/planning.md), [adjudication](../../references/review.md), and [artifact layout](../../references/artifacts.md). Entity/kind review criteria remain explicit in the prompts.
