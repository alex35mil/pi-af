# Review extension

Registers native deferred `review_epic`, `review_task`, `review_gig`, `record_review_response`, and the entity-specific `prepare_epic_plan_presentation`, `prepare_task_plan_presentation`, and `prepare_gig_plan_presentation` tools, and the Task/Gig `prepare_task_completion_presentation` and `prepare_gig_completion_presentation` tools. See [tool discovery](../../references/tools.md). Strict schemas admit Epic planning reviews and Task/Gig plan, interim, final, `conflict-plan`, and `conflict-merge` reviews; each Task/Gig category is its own strict object, so `subject` exists only for interim and the required `resolution` only for `conflict-plan`. A `conflict-plan` round records `conflict.json`: the branch, target, fetched target SHA, resolution, and pre-merge base, which is the branch head or, for an unpushed merge of that target, its first parent. A `conflict-merge` round requires the newest `conflict-plan` round to have approved and the branch head to be a merge whose parents equal that round's pre-merge base and target SHA, and records `merge.json`. Plan rounds snapshot `draft.md`, and final rounds snapshot the kind's ungated working draft (`result-draft.md` or `report-draft.md`), into `candidate.md`. A final round needs no root `result.md` or `report.md`; existing ones are embedded as accepted context. The preparation tools validate and select a reviewed snapshot and return its source and target paths; the write tool presents the approval diff. Plan presentation picks the newest approved plan round. Completion presentation accepts only the newest final round, and only when that round approved, so a newer blocked or failed round never falls back to an older approval.

Also registers `review_pull_request` and `record_pull_request_review_response` for [incoming PRs](../../references/pr/incoming.md). The review tool accepts `reference`, exact configured PR-get `evidence`, a complete local `dossierPath`, and explicit `sourcePaths` for every referenced source/diff/dependency file; the response tool uses the original evidence, returned round number, all findings and status. These distinct adapters require no entity or lifecycle. Review artifacts live under `.project/.local/pull-requests/<number>/reviews/<base-sha>-<head-sha>/review-NNN/`, with write-once source snapshots in `inputs/`. Checkout, state/diffs and working evidence remain at the PR root. Existing review records are not moved or rewritten automatically; round discovery and adjudication use only this review namespace. Each pass freezes its own source bytes so successive uncommitted fix drafts at the same head cannot change earlier evidence. Each reviewer pass records the complete dossier and original-to-saved source-file map, then runs from the trusted maintainer checkout using those immutable inputs. They never call providers, publish, execute contributor code or authorize mutations.

The review subsystem owns prompt assembly, round discovery, signoff validation, optional configured blocked-review confirmation for initialized entities, and reviewed-snapshot selection. `findings.ts` owns finding fields, report parsing, and canonical rendering, including each report-sourced severity beside its ID/title. Parsing accepts exactly one report object surrounded by prose or a code fence, then validates it strictly and names missing or unexpected keys. `agent.ts` owns read-only subprocess execution with shared rules and permissions, in a private session directory that `round.ts` creates per round and always deletes. `model.ts` resolves an explicit reviewer override through Pi’s public model resolver; otherwise it uses the configured startup default, not the parent session’s current model. When Claude Code is selected, it obtains the already-loaded enabled provider extension’s entry point from native `claude-code-status` command provenance and explicitly loads only that provider alongside rules and permissions. It installs nothing and does not guess package paths or execute unrelated extension factories. Standard providers retain native child selection. The child keeps `--no-extensions`, `--no-skills`, and `--no-prompt-templates`. Its tool set is a `ReviewerToolset`: entity reviews get `read,grep,find,ls,git_read` and load `git-read.ts`; incoming-PR reviews get only `read,grep,find,ls`. No write, Bash, Codemode, workflow, or MCP executor is granted. Reviewer tools run under the user's permission settings with no UI, so under `defaultMode: "ask"` they must be allowed by name or they're blocked. `round.ts` shares execution/report/transcript/outcome persistence and complete-list adjudication across entity and PR adapters. When a successful run returns an invalid report, it resumes that session once with the validation error and the previous output in full; both runs share `agent.jsonl`, `transcript.md`, and `stderr.txt`. If that also fails, it writes `invalid-report.md` and includes the output, marked unvalidated, in the thrown error. Entity reviews (`index.ts`) add a fixed pause after two consecutive failed rounds per category, independent of the configured blocked-review threshold; incoming PR reviews have no pause. `pull-request.ts` owns the PR evidence adapter, source-file snapshots, and untrusted-data prompt. Existing entity gates remain in `index.ts`.

`git-read.ts` registers `git_read` only in reviewer subprocesses. It runs one allowlisted subcommand through `execFile` without a shell, with `GIT_TEST_DISALLOW_ABBREVIATED_OPTIONS=1`, hooks, fsmonitor, pager, colour, external diff, signature verification, content filters, and custom merge drivers disabled, and refuses inherited relocation variables. It refuses arguments that write files, run programs, or read untracked, ignored, or out-of-repository content, including any abbreviation of a refused long option, and requires `--write-tree` for `merge-tree`. It reads Git objects and tracked files, so path-based `read` deny rules don't apply to committed content. Every entity review prompt names it through the shared `REVIEW_GIT_INSTRUCTIONS`.

Operational contracts: [planning](../../references/planning.md), [adjudication](../../references/review.md), and [artifact layout](../../references/artifacts.md). Entity/kind review criteria remain explicit in the prompts.
