# Integrations

Registers `/backlog`, `/todo` and the named native deferred context, Resource ID, publication, Phase, and body tools listed in [Workflow tools](../../references/tools.md). Public schemas are operation-specific concrete objects; shared internal dispatch unions remain domain contracts. The agent makes provider calls through registered MCP tools under normal permissions. The harness reads/writes owned local configuration, metadata, artifacts and Resource IDs and validates scoped native operation arguments; the agent executes provider calls directly under configured permissions.

Named integration context tools read local workflow configuration and state without external operations or configuration changes. `inspect_integrations` and `inspect_queue_intake` require `target: "current" | "workflow"` and return `target`/`projectRoot`. The workflow target resolves private global `workflowProject` through `../__lib/project-config.ts`, then reuses the source project's existing tracker schema and readiness checks. It works independently of consuming-project setup; missing configuration produces a small corrective error, not automatic setup. Entity-bound operations remain current-project scoped. It does not inspect provider-tool schemas. Initialized context exposes the shared [Phase](../../references/phase.md) projection contract. `prepare_github_phase_mutation` and `prepare_linear_phase_mutation` validate supplied fresh native facts and calculates an absolute field/full-label assignment locally; the agent applies it through registered MCP tools. Before merging, `prepare_integration_merge` checks that GitHub's PR details match the saved PR and the local branch's commit. It delegates to the same shared forge merge operation used by incoming shipping, returning repository-policy arguments locked to that commit, confirmed merged proof or a blocker. The agent supplies the commit title using the selected commit skill's message rules.

`inspect_incoming_pr_context` accepts `reference` (a GitHub PR URL targeting the current configured repository or `#NN`) without an initialized entity or tracker. It returns the configured forge server, optional GitHub Project lookup/Status mapping, normalized exact PR addressing, local evidence directory and safety boundaries. `forge/github/incoming-pr-context.ts` validates reference and exact PR-get evidence, distinguishes fork head identity from the base repository, and owns safe local evidence paths. It performs no provider calls or branch changes and does not reuse workflow-created PR intent. See [incoming PR handling](../../references/pr/incoming.md).

`plan_incoming_pr_merge` validates actual reviewed/fresh PR evidence and delegates to `forge/github/merge.ts`; Deliverable `shippingReadDecision` uses that same fixed repository merge operation. The `plan_incoming_pr_intake`, `plan_incoming_pr_review`, `plan_incoming_pr_shipping`, and `plan_incoming_pr_cancellation` tools validate scoped field/membership evidence and returns only the next native add/Status/close arguments or an unchanged/blocked outcome. No initialized entity, provider execution, approval token, contributor activity inference or In Progress/Phase projection is introduced. See [Project handling](../../references/pr/project.md), [shipping](../../references/pr/shipping.md) and the [shared merge contract](../../references/integrations/forge/merge.md).

`prepare_tracker_publication` prepares native GitHub plan-comment or Linear attached-document calls without calling providers; `record_tracker_publication` and `recover_tracker_publication` persist actual creation/recovery evidence. Requests remain in original titles/names/descriptions. `plan-publication.ts` owns portable state/token contracts; `plan-comment.ts` and `plan-document.ts` specialize identity schemas. `tracker-publication.ts` owns shared orchestration, queued atomic metadata writes and tool registration; provider adapters own native arguments, scope and pagination. `publication-evidence.ts` validates registered evidence without making portable schemas depend on Pi. Tracker records retain `planComment`/`planDocument` state and creation token/native ID/URL, not disposable Resource IDs. Pending-create recovery takes the approved source: one scoped marker match is recorded, no match on a complete read returns the same create with the saved token, and several stop without replacement. `prepare_tracker_publication_update` takes the reads prepare requested: Linear always needs full document and parent reads before an ID-only content update. Every update to a published plan, for any entity, reads it first: `plan-announcement.ts` diffs the restored published source against the new one (`plan-diff.ts`) and renders the announcement comment; the record keeps `planAnnouncement` (`plan-update`, then `announcing`) until the comment is recorded or recovered by its marker. Document recovery completes cursor listings, then requests full reads for matching-parent candidates because previews are truncated. The operation returns complete read-back content for uncertain-update comparison. Linear initialization does not insert or require an embedded workflow ID; native bindings, Phase and other metadata management remain unchanged.

`render_provider_body` accepts the complete approved source and configured destination, then delegates presentation to `projection.ts`. Publish its exact returned Markdown; the workflow publication layer applies the message's attribution separately. The renderer and source artifacts stay signature-free. It performs no provider calls or source/index writes; invalid source layout fails locally. See [source shape](../../references/artifacts.md#reviewed-document-shape) and [publication/approval rules](../../references/integrations/shared.md#provider-bodies).

`set_github_workflow_phase` and `set_linear_workflow_phase` validate active lifecycle and observed native facts before updating existing Phase metadata, and return any native reconciliation assignment. They execute no provider calls and change no branch or lifecycle. The pure operation lives in `phase.ts`; `operations.ts` owns thin Pi registration, per-file mutation queues and persistence. See [Phase](../../references/phase.md).

`plan_epic_task_issues` and `record_epic_task_issue` (`epic-task-issues.ts`) keep one tracker issue per accepted Epic Task. Planning reconciles the parsed `## Tasks` sections against supplied fresh child-issue facts and returns ordered native creates, tags, board repairs, and guarded cancellations, `complete`, or `blocked`; it keeps no saved progress, so reruns finish interrupted work. Recording validates the create evidence and tags the Task heading once, refusing duplicate markers. See [Epic Tasks](../../references/epic-tasks.md).

`resolve_resource_ids`, `record_resource_ids`, and `invalidate_resource_ids` use scoped IDs/URLs from `resource-ids.json` and records actual adoption, mutation or required-read evidence. Missing/stale IDs require agent investigation. Scoped cache mutation is queued/atomic, preserves unrelated entries and remains outside Git; the operation memo resets on context/shutdown/reload.

Before the PR create, forge `begin_resource_creation` saves immutable repository/head/target intent in the local metadata. After one native PR-create call, `record_resource_creation` writes returned number/URL directly to the IDs file. Explicit `select_pull_request_resource` updates that same file. Neither operation changes `metadata.json` or creates another artifact. Uncertain outcomes require agent investigation before retry.

## Communication attribution
Workflows own communication attribution for the official GitHub (`https://api.githubcopilot.com/mcp/`) and Linear (`https://mcp.linear.app/mcp`) registrations. Loading the workflow integration extension installs publication independently of consuming-project configuration or initialized entities. Generic MCP alone leaves native communication unchanged.

AI-assisted communication receives a code-owned footer:

```text
Sent via Pi. Model: provider/model-id.
```

The harness name comes from the running Pi package (`Pi` for the default harness; custom names are preserved). Provider/model ID come from the current execution context, including configured gateway names and full IDs. GitHub uses `<sub>…</sub>`; Linear uses Markdown italics. The footer is a final paragraph without a new divider, outside folds and after closing references. Content edits replace a terminal signature, including the earlier bracket format; repeated preparation does not duplicate it. Repository files and source artifacts remain signature-free.

Mapped tools expose local `__pi_authorship: "ai-assisted" | "user-verbatim"`. The agent automatically chooses `user-verbatim` for a complete user-written message relayed unchanged; no special opt-out wording is required. This preserves the exact text without adding or removing a footer and needs no model identity. Agent-written, reworded, expanded, or generated/quoted messages use `ai-assisted`, also the default when omitted. The agent identifies authorship intent; code enforces that per-call choice and strips the local field before native execution.

Coverage includes GitHub issue/PR bodies, comments, replies, textual reviews and Project status updates; Linear issue/Project descriptions, comments, documents, milestones, releases, release notes and status updates. Initialization, queues, accepted artifacts, and external discussions use the same boundary. Only explicit operation/content mappings are prepared. Metadata-only changes, reactions, controls, reads, deletions, titles, labels, attachments, repository/file content, and Git operations remain unchanged. Unknown services and arbitrary stdio aliases are not inferred to be GitHub/Linear.

Content edits require complete text. Patch-only or template-only content writes stop locally with a request for complete text; needed reads remain explicit registered calls under normal permissions. Nonempty AI-assisted text requires current model identity. Signing adds no prompt, preview, approval lane, hidden provider call, retry, or permission bypass. Existing workflow lanes and permission settings alone govern confirmations.

Mapped tools also carry `REVIEW_GUIDANCE` in their description, ahead of the authorship guidance: before a call that creates or changes message text, the agent shows the user the complete text and destination and waits for approval, except for explicit send-without-review, content from an already approved artifact or workflow step (including its code-rendered body), or an unchanged user-supplied message. This is agent guidance only; the publication code still adds no prompt and doesn't block unapproved sends. The `__pi_authorship` schema description carries only the authorship guidance. The shared rule lives in [sending messages](../../references/communication.md#sending-messages).

### Publication boundaries

Publication policy belongs to `publication.ts`; the reusable Pi wrapper and runtime identity reader live in `publication-tool.ts`; MCP attachment lives in `publication-mcp.ts`. These modules prepare attribution, not the generic transport or agent-written prose. Provider recognition is shared with workflow MCP setup inspection.


- [publication.ts](publication.ts): transport-independent operation/identity types, mappings, authorship, schema/guidance preparation, formatting, and wire cleanup. It has no MCP or Pi execution dependency.
- [publication-tool.ts](publication-tool.ts): Pi tool-definition wrapping and lazy runtime identity. It delegates once, preserves native execution arguments/context/results and unrelated definition fields, and knows no custom MCP naming, configuration, catalog, or events.
- [publication-mcp.ts](publication-mcp.ts): current bridge metadata conversion and registration only, using the generic [tool-decoration contract](../../../extensions/mcp/README.md#tool-decorators). Official-provider recognition is shared with workflow MCP setup inspection.

Backend-specific registration and original operation identity belong in the binding. Changing the MCP backend leaves publication policy and the reusable Pi wrapper independent of its configuration, catalog, events, and generated tool names.
