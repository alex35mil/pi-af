# Plan

## Overview

Support `/pr <URL>` and `/pr #NN` for taking existing GitHub contributions through Project intake, private review, approved updates, shipping or cancellation without initializing an Epic, Task or Gig. Contributors do not need to use pi-af or update board status.

### Plan highlights

- Offer fork-only automatic Project intake through Project Setup: add new fork PRs and use the Project's configured Backlog default; exclude same-repository PRs, including Deliverables. Explicit /pr intake covers other or missing PRs with a Backlog/Todo choice and preserves existing cards. Maintainer review moves to In Review and stays there until confirmed merge/Done or close/Canceled.
- Use one shared repository merge operation for Deliverables and incoming PRs: the existing fixed squash strategy and verified expected head, not a second method choice or copied policy. After accepted fixes and fresh verification, the exact ship/merge request covers that shared merge, Project Done and safe local checkout cleanup as one set. Cancel closes the PR and sets Canceled while preserving local work.
- Review contribution code privately and present an evidence-backed 1–5 malicious-code assessment before checkout. Every score requires explicit checkout approval.
- Registered tooling owns checkout and Git orchestration. For an approved update, use **standard rebase → approved conflict resolution → immediate SHA-pinned `--force-with-lease` PR update → approved fixes and maintainer testing**.
- Keep the provider's PR evidence unchanged. Observe the actual target branch tip separately, and pin both the rebase target and the contributor-branch push lease to exact observed commits.
- Preserve unexpected work and incomplete operations, keep the parent repository/session untouched, and prevent automatic Git helpers or contributor-code execution. Rebase approval covers its replacement commits, not later fix commits, tests, review publication or GitHub merge.
- Keep checkout/state/diffs and working evidence at the private PR root; keep immutable review rounds under `reviews/<base-sha>-<head-sha>/review-NNN/`. Update this unshipped contract directly without moving existing records or adding migration/compatibility machinery.

## Selection, identity and storage

The thin `/pr` command routes an explicit reference to the `pr` skill; empty input shows usage. Read actual membership first: configured fork-only automation may already have added the PR to Backlog, and an existing item needs no intake-choice prompt or reset. Explicit manual intake asks Backlog or Todo before adding a missing PR to the configured Project. That explicit choice approves only the scoped membership and initial Status update, not review publication, checkout, fixes, pushing, closing or merging. An explicit maintainer request to start reviewing approves the scoped In Review update and private review, not those other mutations. Ordinary resume preserves existing board progress. Do not infer a PR from a tracker issue or current branch.

Use the current project's configured GitHub forge. `#NN` and HTTPS `github.com/<owner>/<repo>/pull/<number>` URLs must target that configured repository; reject foreign targets before provider calls. Accept positive safe-integer PR numbers and ordinary trailing slash/query/fragment components. Missing/invalid configuration, malformed references and non-PR URLs stop the operation. Contributor heads may be forks.

The entity-independent `integration_context` incomingPullRequest operation returns normalized addressing, configured server/read arguments, private root, checkout/reviews paths, safety guidance and the configured GitHub Project integration when available. Use the GitHub tracker's Project and Status mapping, with its own registered MCP server, independently of forge addressing; do not adopt its issue or entity contract. With no GitHub Project configured, report that board handling is unavailable while retaining existing forge-only private inspection. Do not invent a destination, infer one from PR metadata, or create a Linear issue instead. Validate artifact persistence and require no initialized entity. Context and local transition planning make no provider calls or branch changes.

`integrations/forge/incoming.ts` owns exact identity. Validate actual configured `pull_request_read:get` evidence: tool, arguments, PR URL/number, base repository/ref/full SHA and head repository/ref/full SHA. Derive repository identity from `repo.full_name`; optional expanded owner/name metadata must agree. Identical ref names across repositories are not identity. Missing/deleted head-repository metadata prevents fetching/writing that head; never substitute the base repository.

Separate three facts in the checkout model:

1. Original provider-reported PR revision and its actual evidence, retained unchanged.
2. Actual Git observations of the verified target repository/ref and contributor repository/ref, including their full SHAs. The target observation is not a replacement provider base SHA.
3. Local working baseline and the last confirmed published contributor head. These advance only through validated tool operations and confirmed remote observations.

Bind operations to stable PR repository/number and exact base/head repository/ref identities. New provider responses remain actual responses, not fabricated copies with edited SHAs. Before a new rebase, require the observed contributor branch to match the managed published source head and fresh provider head; otherwise stop for reassessment. After our confirmed push, accept fresh provider evidence for that known published head without overwriting original evidence. Report provider base-SHA changes separately and reassess affected approvals; a retargeted PR or unexpected contributor head never authorizes automatic repair. Read-only inspection can report mismatches without changing checkout work.

All incoming work stays outside Git at `.project/.local/pull-requests/<number>/`:

- `checkout/`: independent repository with its own real `.git`, objects, HEAD and index.
- Checkout identity/progress, remote observations, inspection/diff files, safety assessment, dossier, notes and mutable source/dependency evidence: at the PR root, outside `checkout/`.
- `reviews/<base-sha>-<head-sha>/review-NNN/`: review-specific metadata, original evidence, saved dossier/source map, report/adjudication/transcript/outcome and write-once `inputs/` source snapshots.

The existing `.project/**/.local/` ignore rule in versioned mode and `.project/` exclusion in unversioned mode cover this entire area. Add no ignore rule, workflow ID, initialized-entity lifecycle, branch contract, replacement PR or versioned incoming-PR artifact. Native PR Project membership and Status are managed separately from initialized entities. Existing review records are not moved/rewritten; round discovery and adjudication use only the current reviews namespace. Old notes/state are evidence, not freshness or approval authority.

## Maintainer-controlled Project flow

Track the existing PR as a PullRequest Project item, not a duplicate issue. Read membership and the configured single-select Status field through the configured registered Project MCP server, finishing pagination used to establish absence. Match exact Project owner/type/number and PR base repository/number; numeric issue and PR numbers alone are not membership identity. Preserve existing items, unrelated fields, labels, Priority, Phase and Internal ID. Assign no workflow ID, Kind, Phase, linked-issue lifecycle or contributor activity state.

| Maintainer action / observed state | Project behavior |
| --- | --- |
| Enabled automatic intake, verified open fork PR | Add Project membership only; the existing native Backlog default initializes new items. Repeated/reopened events preserve any existing item's Status. Same-repository PRs are excluded. |
| Explicit /pr intake, membership absent | Ask Backlog or Todo. After that exact scoped choice, add the selected PR with item_type pull_request, then set only its configured Status to the chosen value. Do not start reviewing merely because intake completed. |
| Ordinary intake/resume, membership present | Preserve membership and current progress; do not re-add, requeue an In Review item, or reset a terminal item. Resolve missing or conflicting Status through maintainer direction rather than a guessed default. |
| Explicit start/continue review, open PR | Set In Review, or do nothing when already In Review. Require the existing intake/membership step when missing. Do not silently reopen terminal work. |
| Feedback, Request Changes, contributor pushes, draft changes, rebase, fixes, tests or later fix publication | Keep In Review. These events never choose another board status. |
| Ship, merge confirmed for the exact PR | Set Done; never mark Done just because local review, a commit, a push, CI or an approval succeeded. |
| Cancel, close confirmed without merge for the exact PR | Set Canceled after closure. Cancellation closes the PR, not merely this review session. |
| Merge/close not confirmed, denied or failed | Preserve the nonterminal board state and local work. Report confirmed partial operations and the remaining blocker. |
| PR is already merged or already closed without merge during terminal reconciliation | Reuse verified outcome: Done for merged, Canceled for closed/unmerged. Do not repeat confirmed merge/close or reopen anything. |

The agent drives these explicit maintainer actions using native registered MCP calls. Add a focused entity-independent Project transition planner at the incoming integration boundary, exposed through the existing integration_context tool. It validates configured destination, exact PR evidence and fresh scoped membership/Status facts, then returns only the required absolute native operation arguments, or an unchanged/blocked outcome. It grants no approval and stores no local lifecycle authority. Model missing versus present membership explicitly; preserve the chosen initial status across the add-then-set sequence. Reconcile uncertain membership creation with exact reads before another add, and uncertain field writes before retrying; do not blindly create duplicates or reset progress on resume.

Use projects_write add_project_item with item_type pull_request and the actual pull_request_number. Use the verified Project item ID for field updates; do not resolve a PR through an issue-only identity path. Read and verify required outcome facts absent from mutation success responses. Skip already-applied absolute Status assignments. Missing/ambiguous membership, wrong content type/repository, incompatible fields/options, unavailable tools or denied access block board mutation rather than a destination or status fallback. A configured board failure is visible, not silently ignored or reported as synchronized.

Outside the explicit fork-only intake Action below, add no background reconciliation, contributor status commands or event-driven lifecycle transitions. Existing Project settings remain user-owned. When observed settings or external writes prevent the agreed state from holding, report that blocker rather than fighting it or claiming guaranteed synchronization. Agent Project writes remain under configured MCP permissions; do not change credentials, permissions, secrets or provider settings automatically.

Ask during setup for a GitHub-valid Actions secret reference, never its value, and never read/copy MCP credentials into Actions or committed files.

Setup must explain and require confirmation of the selected secret/access, applicable fork/event policy, Backlog default and workflow deployment prerequisites before claiming automation ready. Preserve existing native Project automations and guide only explicitly approved corrections to overlapping broad auto-add or conflicting Status rules. The fork-only Action is independently approved hosted automation, not an agent API fallback after an MCP denial. Without confirmed prerequisites report prepared/pending, not active/successful automation. Development tests use local/mocked API fixtures only; do not enable or run the workflow against actual repositories, Projects or #13.

## Registered checkout and rebase operations

Extend `incoming_pull_request_checkout` in the existing PR extension. Use strict operation-specific inputs: common selected `reference` and actual configured PR-get `evidence`; the rebase operation additionally names expected target/source SHAs from the tool's Git observations; continuation names exact approved resolution paths. Do not accept arbitrary commands, repository URLs, branch overrides, checkout directories or approval booleans. Derive repositories/refs from validated PR identity and validate full Git refs before transport. No agent-generated Bash orchestration or manual fallback after refusal/unavailability.

Represent checkout, active rebase, completed-but-unpublished rebase, approved fix-commit intent, committed-but-unpublished fixes and the current published working baseline as distinct validated states, not optional flags compensating for an original-head-only model. Persist exact identity/progress facts and inspect native Git state on every call; never persist a durable approval grant. Keep one active rebase/push intent per managed checkout with its source head, target SHA, lease, native progress and resulting head. Preserve prior immutable reviewer evidence across every phase.

| Operation / situation | Required behavior |
| --- | --- |
| `prepare`, new approved path | After object-operation approval, initialize an independent object repository with an empty template. Fetch exact provider base/head commits from their respective verified repositories, without tags/submodules; verify commits and compute their merge-base. Leave source/configuration unmaterialized. |
| `prepare`, existing managed state | Validate/report actual state without re-fetching over work or resetting it. Unmanaged/incompatible existing paths are preserved and refused, not silently adopted/converted. |
| `checkout`, valid object-only state | After safety assessment, explicit checkout approval and fresh matching evidence, require no unexpected source/index/HEAD. Materialize detached exact contributor head; verify it, then soft-reset only HEAD to the computed review merge-base. Index/source remain at contributor head, exposing contributor-only staged changes. Repeated valid review setup is a no-op. |
| `beginFixes`, finished contributor review | After approved corrections and confirmation of no unsaved editor buffers, require expected detached review HEAD, original-head index/source and no untracked files including ignored additions. Restore and verify the clean contributor head. This clean fixes state permits either approved static edits directly or the separately approved rebase before any fixes. |
| `observeTarget` | Under approved Git-read scope, derive target and contributor repository/full branch refs from PR evidence and read their current tips. Return/store actual observations separately from provider revision and any active pinned rebase intent. Do not change checkout source/index/HEAD or silently replace an active target/lease. |
| `rebase`, clean fixes state | Require approval of standard rebase plus immediate PR update, exact observed target SHA, exact source/contributor destination and expected remote-head lease. Establish consent/access first. Re-read refs before starting; changed target/source observations stop before rewriting. Require clean detached HEAD/index/source at managed published head, no untracked files and no existing Git operation. Fetch the pinned target commit, record source/target/progress, then run standard rebase. |
| Rebase stops with conflicts | Treat verified native rebase/conflict state as an inspectable outcome, not generic rollback or success. Return affected files, unmerged index stages, progress and relevant diffs. Preserve intermediate rewritten commits, source and index. No push while conflicts remain. |
| `continueRebase`, approved resolutions | Verify the same source/target intent and native operation. Preserve/refuse unexplained index, metadata, outside-path edits or untracked additions. The agent edits approved resolution contents; the tool stages only exact approved paths, including approved deletions, and continues without an editor. Another conflict is returned for the next approved resolution. When rebase succeeds, immediately run the pinned-lease publication step. |
| Rebase succeeds without conflicts | Verify the resulting detached head, completed native rebase, target ancestry and clean index/source; record the result before publication. Immediately push that result to the same contributor branch with the exact lease, without waiting for later fixes/testing or adding an unrelated fix commit. |
| `publishRebase`, failed/interrupted/uncertain publication recovery | Require the recorded rebased head and clean local state. Read the exact remote branch: result SHA already present means confirmed publication without another push; original lease SHA still present permits an explicitly approved retry of the same intent; any other/missing head blocks. Do not refresh the lease, recreate the branch, overwrite new contribution work or rebase again automatically. |
| `inspect`, any managed phase | Return recorded and observed state, original/current/provider revisions, target/lease facts, conflicts/progress, working baseline, staged/unstaged/untracked state and publication outcome. Report mismatches without modifying HEAD/index/source or attempting recovery. |
| Dirty/wrong-state mutation, changed identity, unexpected work or incomplete operation | Refuse the mutation and preserve actual files/index/HEAD/native progress. No automatic reset, cleanup, stash, abort, skip, force checkout, rebase restart, branch replacement/deletion or unprotected push. Recover only through a separately agreed action supported by verified state. |

Contributor review is read-only: no edits, staging/unstaging, commits or pushes in its staged representation. Never mix that contributor-review representation with maintainer edits. `beginFixes` restores ordinary clean Git state before either rebase or static fixes. Repeated calls in a valid fixes state report drafts without resetting them. Rebase is opt-in, not an automatic response to a newer target.

Use **standard linear Git rebase** onto the exact approved target: merge commits are not recreated, ordinary already-upstream/empty-commit handling applies, and Git's skipped-commit information is reported. Pin noninteractive behavior explicitly instead of inheriting topology, autosquash, autostash or other-ref updates from host configuration. No arbitrary todo editing, exec commands, automatic conflict-side choices or merge-into-PR substitute.

The approved rebase-and-update set includes the replacement commits created by rebase and the approved manual conflict resolutions. It does not authorize extra fix commits, tests, publication of GitHub reviews/comments or GitHub merge. The expected target stays pinned through conflict resolution; later observations are reported separately, never substituted silently. A remote contributor update invalidates the push lease, not permission to choose a newer lease automatically.

Push only the exact recorded rebased SHA to the exact verified contributor branch, using `--force-with-lease=refs/heads/<head-ref>:<observed-pre-rebase-head-sha>` and an explicit source-SHA-to-destination refspec. Never use plain `--force`, an implicit tracking-ref lease or wildcard/matching pushes. The actual fork repository/ref, not the base repository or a same-named branch, is the destination. Recheck and report the remote outcome. A rejected lease stops and preserves both remote work and the local rebased result.

Record a push attempt before sending it. Network failure/process interruption can leave the remote updated even when the client reports failure; reconcile with the exact remote head before any retry. A tool failure after confirmed publication reports that completed remote step and remaining blocker rather than rolling it back or claiming nothing happened. After publication, obtain fresh actual provider evidence and reassess review/CI/publication inputs for the new PR head. Provider responses are never edited to manufacture that confirmation.

## Managed additive fix delivery

Extend the same registered checkout boundary with commitFixes and publishFixes. They derive source, destination and baseline from the managed PR; callers supply no branch, URL, arbitrary revision or Git command override. commitFixes accepts the exact approved checkout-relative paths and commit message. publishFixes uses only the recorded additive commit result. These are separately approved operations, unlike the combined approved rebase-and-immediate-update set. No direct Bash commit/push route is used to bypass managed state.

The verified owning defect is that current fixes validation requires HEAD to equal baselineSha, while documented later shell commits/pushes advance HEAD/remote outside that state. Such an approved shipment makes subsequent inspection/resume invalid. Fix this at the checkout/state/inspection abstraction, not by loosening one caller or hand-editing records.

| Operation / state | Required behavior |
| --- | --- |
| Accepted fix draft, commitFixes approved | Require detached HEAD at the confirmed published baseline, expected index/native state, fresh matching PR evidence, contributor consent/access, no unsaved buffers and a complete approved path set. Refuse unexplained staging or changed/untracked paths outside that set. Stage exact literal approved paths, including approved additions/deletions, and create one additive commit with the exact approved message and no hooks, signing, editor or contributor-code execution. Do not push. |
| Local commit intent/result | Record intent before commit and its validated result afterward. Validate the expected parent, committed tree, message and clean resulting HEAD. Preserve index/source and incomplete work on failure or interruption; no reset, amend or cleanup. Inspection remains available. A fresh explicitly approved recovery may recognize only the exact recorded intent/result; never create a duplicate commit or adopt an unexplained HEAD. |
| publishFixes approved | Require the recorded clean additive result and exact verified head repository/ref. Observe the remote first: already at result confirms success without another push; still at the recorded source baseline permits the approved normal non-forced source-SHA push; changed/missing head stops for reassessment. Never use force, rebase, lease refresh or an implicit branch destination for later fixes. |
| Failed/uncertain fix push | Preserve the local commit and publication facts. Observe the exact remote before an approved retry. Confirm an already-applied result without duplication; do not recommit, overwrite newer contribution work or claim success from an attempted push alone. |
| Confirmed fix publication | Advance the working baseline to that confirmed head, retain original provider evidence and historical rebase facts, then obtain fresh actual PR evidence. Inspection, further approved uncommitted drafts and resume accept the managed published head. Record facts never become approval tokens. |

Keep the current valid prepared/contributorReview/fixes/rebasing/rebased records readable without migration or automatic rewriting. In particular, preserve existing completed-but-unpublished rebase recovery and its exact original lease. A historical published rebase result and the current published baseline are different facts once additive fixes are published; update that owning invariant and validate their actual Git relationship instead of treating every later baseline as corruption. Extend the domain with explicit fix-delivery states, not compatibility flags or caller-specific exceptions.

Inspection distinguishes original contribution, actual rebase integration, already-published additive fixes, pending additive commits and the current-baseline-to-draft diff. In particular, original-to-rebase evidence ends at the recorded rebase result rather than accidentally including later fix commits. Keep complete evidence at the existing private PR root and freeze relevant inputs per review pass; no record/snapshot relocation. A successfully published fix does not imply passing CI or merge readiness.
