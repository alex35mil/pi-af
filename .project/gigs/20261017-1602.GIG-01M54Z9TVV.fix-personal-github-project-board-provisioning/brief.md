# Brief

Fix personal GitHub Project Board provisioning failing with 404

## Problem

Project setup partially provisions a personal GitHub Project, then fails with:

GitHub API failed with status 404: Not Found

The Project, repository association, and configured fields remain, but the requested Board is absent. Setup cannot finish automatically.

## Reproduction

1. Run project setup for a personal GitHub repository.
2. Select versioned artifacts, GitHub tracker and forge, and identifier-title branches.
3. Choose the repository's personal account as Project owner.
4. Create a public Project, enable repository association and default repository, and accept default metadata and Board presentation.
5. Approve the exact provisioning preview and apply it.

Observed configuration used a classic personal access token with project and repo scopes and API version 2026-03-10.

## Expected behavior

Create and verify the Board with:
- Configured visible fields.
- Status columns.
- No swimlanes.
- Priority as the sole sort: Urgent → High → Medium → Low.

Delete only the captured, unchanged autogenerated default view after successful verification. Return tracker configuration and the remaining manual steps.

## Actual behavior and partial state

Apply returned the generic 404 error without identifying the HTTP method, endpoint, or provisioning stage.

Read-only reconciliation confirmed:
- The public Project was created and remained empty.
- The repository was associated.
- Status, Phase, Priority, and Internal ID fields were configured.
- Only the autogenerated table view, View 1, existed.
- No Board existed.
- No consuming-repository workflow files were written.

Repository-label state was not independently reconciled after failure.

## Investigation evidence

Affected implementation:
- workflows/extensions/project-setup/github-project.ts
- createBoardView resolves the account's numeric REST ID, then posts to:
  /users/{numeric_id}/projectsV2/{project_number}/views
- REST requests use API version 2026-03-10.
- The shared error formatter drops request method and path.
- Board creation catches failures and checks for a newly created matching Board before rethrowing; no matching Board was found here.

Live read-only checks with the same token showed:
- GET /users/example-owner → 200.
- GET /users/{numeric_id}/projectsV2/{project_number} → 404.
- GET /users/example-owner/projectsV2/{project_number} → 200.
- GET on both corresponding /views paths → 404. These reads do not establish whether either POST route works.

Current GitHub view-creation documentation names the parameter user_id and describes it as a unique user identifier. The implementation and workflow guidance interpret this as numeric. Project-read documentation explicitly uses username.

The numeric-owner assumption is a suspect, not a proven root cause. No username-based Board-create POST was attempted.

## Tests and guidance

tests/workflow-github-project-setup.test.ts mocks personal Board creation only at /users/42/projectsV2/.../views, repeating the implementation's numeric-owner assumption.

The same numeric-user requirement appears in:
- workflows/skills/project-setup/SKILL.md
- workflows/references/setup.md

## Required investigation and correction

- Establish the exact failing request and correct personal-owner Board-create contract.
- Fix the owning provisioning implementation and any affected guidance.
- Add regression coverage grounded in verified API behavior.
- Make failures identify the safe request method/path and provisioning stage without exposing credentials.
- Preserve partial Projects and existing views; do not blindly recreate Projects or retry uncertain creates.
- Keep provider mutations behind exact provisioning-preview approval.
- Do not treat a manual Board workaround as the workflow fix.

## Evidence limitations

The installed workflow revision was not established. The inspected workflow source was the configured source checkout; exact equivalence to the running installed copy was not independently verified.

No workflow code changes were made during diagnosis. A new recovery feature was discussed but was not approved or implemented.
